paralever

The command line

One file in, and one of four things out: a verdict, a run, a parallelization, or a Lean file that proves the program's parallel reading equals its sequential one. The last is the point of the tool.

A checker that prints race-free is a linter, and you believe it or you do not. A tool that writes a module which Lean then checks is different in kind, because the claim leaves with its proof attached.

console 
lake build paralever                      # ./.lake/build/bin/paralever

paralever check   Examples/Language/sum.prl
paralever prove   Examples/Language/sum.prl -o Proofs/Sum.lean --check
paralever to-mlir Examples/Language/sum.prl -o sum.mlir
paralever to-prl  Examples/Mlir/doall-no.mlir

Both front ends, one program

Every command takes a .prl file or a .mlir module in generic form, because both compile to the same pair — a Layout saying where the buffers are, and an unrolled ParProg.

The commands

CommandWhat it prints

run FILE [--threads]the heap after a run, buffer by buffer

autopar FILEthe parallelized program as .prl, with the plan's numbers
prove FILEa Lean module stating what holds of the program
to-prl FILEthe program as .prl
to-mlir FILEthe program as MLIR generic form
to-lean FILEa Layout and a paralever { … } block
OptionEffect
-o PATHwrite there instead of to standard output
--threadsrun one Task per thread of every fork rather than the canonical order. The heap is the same one, which is what runTask_eq says for every program wfB accepts
--autoparmake prove, to-mlir and to-lean take the parallelized program as their subject
--checkrun lake env lean on what prove wrote, and report Lean's verdict rather than the tool's
--colourpaint to-prl's output in the editor grammar's token classes

check exits 1 when the program has a race, so a build can gate on it:

console 
for f in Examples/Language/*.prl; do paralever check "$f" || echo "$f is racy"; done

What prove writes

Three cases, and no choice about which one applies. The program decides, by which check it passes.

The programThe theoremHow
wfB = true ParSeqEq at every heap and register file ParProg.par_seq_eq (by decide) ρ σ
wfB = false, but the exact check accepts at the declared heap ParSeqEq at that heap parSeqEq_of_runSeq_eq from the exact check
both refuse no theorem; both refusals, proved by decide on each

The first case, which is what the library is for

wfB decides Bernstein's condition at every par node by reading the syntax, so it holds at every heap — and that is exactly par_seq_eq's hypothesis.

Lean 4 · written by paralever prove

The second case: a computed address

dst[%i] has a footprint of all of dst, because the index is not known from the syntax, so two threads that write distinct cells still look like they collide and wfB refuses. The per-heap check measures the accesses along the canonical run instead, and accepts — which buys the equivalence at the heap the file declares, and nowhere else.

Lean 4 · written by paralever prove

The third case: a real race

The generated file says so and proves both refusals. No theorem of this shape exists for such a program: its parallel reading reaches wrong, which is no terminating outcome, while its sequential reading terminates. paralever race FILE prints the interleaving that does it.

And what --check reports on it:

console 
$ paralever prove Examples/Language/chain.prl --autopar -o /tmp/Chain.lean --check
written to /tmp/Chain.lean
lake env lean /tmp/Chain.lean
/tmp/Chain.lean: Lean accepts it

Three details of the generated module. It reads the source through prl_file or mlir_prog, which compile the file while the module elaborates, so by decide sees a program literal and never runs the reader. The path it names is relative to the module's own directory when the two live in one tree, and absolute otherwise. And --check shells out to lake env lean, so the tool reports Lean's verdict rather than its own.

The four reports, also inside Lean

The executable is a thin wrapper. The same four views are #evals over a program read at elaboration time, so a file can be the subject of a theorem without a build step in between.

ViewWhat it prints
checkReportdeclared memory, footprint by name, thread count, rounds, verdict
runReportthe buffers after a run, sequential or on real threads
raceReportthe interleaving that realizes a race, replayed against step
parReportthe rewrite's output as .prl, with the plan's numbers
paralever run Examples/Language/sum.prl 
A [6] @0  [1, 2, 3, 4, 5, 6]
out [3] @6  [3, 7, 11]

With --threads the same program runs one Task per thread of every fork, and prints the same table. That is not luck: runTask_eq proves the threaded run leaves the heap the canonical order leaves, for every program wfB accepts.

The two conversions

to-prl on a .mlir file and to-mlir on a .prl file are the same program printed by the other front end's printer, with the reader's approximations as comments at the top. Here is doall-no.mlir coming back as .prl, its affine.parallel unrolled into eight threads:

paralever to-prl Examples/Mlir/doall-no.mlir 
buf A[8] = 1, 2, 3, 4, 5, 6, 7, 8
buf B[8] = 10, 20, 30, 40, 50, 60, 70, 80
buf C[8]

parallel {
  %0 := A[0]
  %1 := B[0]
  C[0] := (%0 + %1)
} | {
  %0 := A[1]
  %1 := B[1]
  C[1] := (%0 + %1)
} | {
  …six more threads…
}

A full cycle changes one thing: MLIR globals must carry an initial value, so a buffer the .prl file left implicit comes back as buf out[4] = 0, 0, 0, 0.

What to-mlir cannot do is refuse quietly. Three programs have no generic form in the supported operation set, and each gets a named error: a file with a conditional or a loop, a computed subscript into a multi-dimensional buffer, and a layout where a free returned space so two buffers share cells — two MLIR globals cannot alias.

Limits

  • ▸

    prove writes; Lean checks. Without --check the tool does not run Lean, so a module it writes for a large program can still be slow to check or exceed the recursion bound — decide reduces the program against a heap. The generated module raises the bound and says why.

  • ▸

    --check needs the repository. It shells out to lake env lean, so it has to run from a directory where lake resolves this package.

  • ▸

    One function per module. An MLIR file with several functions and none called main is refused rather than guessed at, because interprocedural calls are not supported.

  • ▸

    The subject is the whole program. There is no option to name an entry region; a labelled region is reachable from Lean with ParProg.findLabel.

  • ▸

    Registers come back renumbered through MLIR. SSA values are not assignable, so a register assignment with no memory in it is inlined into whatever reads it. The program's memory, footprint, verdict and heap are unchanged, which is what the round-trip gate compares.
