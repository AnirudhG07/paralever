paralever

Finding races

When the check refuses, the question changes from "is it safe?" to "show me". Two phases: a scan that is exactly the proof obligation, and a search aimed by what the scan found. The schedule it returns is replayed against the real semantics before it is believed.

Two phases, and what joins them

Phase 1's output is not a yes or no. It names the locations, and phase 2 uses them — which is the difference between a linear walk and an exponential one.

Phase 1: an empty site list is the proof

raceSites p σ walks the term along its reference run and collects, at every fork, every pair of children whose footprints conflict, together with the offending locations. It is a list, not a verdict, and its emptiness is equivalent to well-formedness — proved, both directions:

That equivalence is what makes the tool more than a linter. A linter reports "no races found" and you believe it or you do not. Here, a clean scan is a term of type WellFormed p σ, which is precisely the hypothesis par_seq_eq wants. Zero false negatives is a theorem, not a tuning result.

The scan is complete because step checks for a conflict before letting anyone move, so detection is instantaneous rather than retrospective. Note the absence of a read/read clause:

the conflict test 
conflict(a, b)  =  loc(a) == loc(b)  &&  (isWrite(a) || isWrite(b))

nextAccs(pure _)      = []                 # the actions a thread could do NEXT
nextAccs(read l _)    = [read l]
nextAccs(write l _ _) = [write l]
nextAccs(par cs _)    = concat(nextAccs(c) for c in cs)   # through nested forks

step(par cs k, σ) =
    groups = [ nextAccs(c) for c in cs ]                  # one group per child
    if any two distinct groups contain a conflicting pair:  [wrong]
    else …

Phase 2: left-to-right is the worst possible order

A race needs two threads poised at conflicting accesses at the same instant. The one move that destroys that position is letting a thread execute its conflicting access and run on — which is exactly what a naive depth-first search does first. It drives child 0 through its access, finds nothing, and then backs up one step at a time until the two sides happen to line up.

Phase 1 already says which locations conflict, so the fix is to try those moves last:

findWrongGuided 
targetsOf(sites) = dedup(concat(s.conflicts for s in sites))   # what phase 1 flagged

consumesTarget(p, σ, targets, i) =          # does successor i give up the position?
    match attribution(p, σ, i).action:
      some a -> a.loc in targets
      none   -> false                       # a join consumes nothing

findWrongGuided(targets, fuel, c):
    if fuel == 0: return NONE
    succs = stepC(c)
    if some i has succs[i] == wrong: return [i]
    hold = [ i for i in indices(succs) if consumesTarget(..., i) ]
    …try the others first, then `hold`

Each thread now advances freely until its next action is a flagged one and stops there. Once two threads are stopped, step reports the race itself and a one-step lookahead returns it. This is a reordering, not a restriction — every successor is still visited, so nothing becomes unfindable. The build checks that the blind and aimed searches agree on every tree of depth ≤ 2 and on random trees, and that every schedule the aimed search returns really reaches wrong.

three forks three threads where the middle one is innocent, and it is the case that matters. Blind, the innocent thread multiplies the backtracking and the cost grows about 14× per two writes added to each side: 2.7 s at eight writes, hopeless at twenty. Aimed, it is 34 ms at sixty, because there is no backtracking left to multiply — the innocent thread's moves are never flagged, so it runs whenever it is reached, and the two guilty threads stop at their conflicting writes.

The right-hand table is a clean program, where every path must fail before "no counterexample" comes back — C(2m, m) interleavings. Guidance cannot help, because there are no conflict locations to aim at. It is also never paid: the search returns immediately on an empty scan, and raceSites_nil_iff justifies that rather than merely excusing it. Phase 1's quadratic term is the footprint representation — Footprint holds List Loc and membership is List.contains — which is deliberate, since every other use of a footprint is a decide-able membership or disjointness check.

The schedule is replayed, not trusted

A Schedule is a list of successor indices — at each configuration, which of the available moves to take. The search produces one; follow walks it against the real step relation, and follow_sound says that a successful walk is a Reaches derivation.

So the printed interleaving is not a plausible story about what might happen. It is a proof object: the heuristic that found it could be arbitrarily wrong without endangering anything, because what is believed is the replay.

What it prints

race.prl is two threads that each log their arrival and then both write x[0].

race.prl 
buf x[1]
buf log[2]

parallel {
  log[0] := 1
  x[0] := 7
} | {
  log[1] := 1
  x[0] := 9
}
paralever race Examples/Language/race.prl 
step:thread  action              state
0:T0         write [log[0]] ← 1  log[0]↦1, x[0]↦0, log[1]↦0
1:T1         write [log[1]] ← 1  log[0]↦1, x[0]↦0, log[1]↦1
2:T1         write [x[0]] ← 9    pending
2:T0         write [x[0]] ← 7    pending
Parallel aborts at Step 2. Reason: T0, T1 write to: {x[0]}.
Parallel: x[0]↦7
Sequential: x[0]↦9

Both actions at step 2 are marked pending: neither ran, because the fork aborted when it saw them. That is the shape of the report throughout — a pending step is an ordinary step that happens not to have run, carrying the heap as it stands at that instant with no cell marked as changed.

The difference is not a heap diff, and cannot be.

wrong is terminal and absorbing, so the parallel program has no final heap, while the sequential one leaves x[0] ↦ 9. Racy programs are excluded, not given a behaviour. Printing the sequential heap beside the abort is there to show what was lost, not to suggest the two can be compared.

A clean program has nothing to show, and says so:

output 
No counterexample: no par node fails Bernstein.
Sequential: 0↦0, 1↦1, 2↦2

A thousand-step trace is a thousand rows and the information is at the end, so the report keeps the first five steps and the last fourteen and collapses the middle into a count with its per-thread split. Location sets, the state column and the schedule all clip the same way. The model behind the text is structured — a step knows its thread, its action and its cells, and a cell knows whether that step changed it — so the same report renders as text in a terminal and as an infoview widget, in the editor's own theme colours.

In tactic position

Two tactics, for a goal you are writing by hand rather than a file you are checking. paralever_race leaves the goal alone — it is trace_state for schedules. paralever_check is the one a proof uses: it tries to prove the goal first, one route at a time, and runs the search only when none of them discharges the obligation. Then it fails with the interleaving attached.

RouteWhat it is
refine par_seq_eq ?_ _ _ <;> grindthe one-liner, with grind on the obligation
the same <;> simp +decide…evaluating it
the same <;> decide…evaluating it in the kernel
parSeqEq_of_runSeq_eq from two wellFormedB_iffsthe per-heap route, for a computed address
par_seq_eq _ _ _ ((wellFormedB_iff _ _).1 ?_)the same for a ParM written by hand

The first route cannot in fact discharge wfB s = true, and is kept first anyway. The obligation is a closed Boolean computation: grind treats wfB s as an atom and has nothing to rewrite it with. The routes after it evaluate the term, which is what this obligation needs. The ladder is ordered so that a future wfB lemma set — for the N-ary kernel shapes, where the program is symbolic and there is nothing to evaluate — is tried before the evaluating routes that could not touch it.

A goal that quantifies over its heap or its register file has no values for the search to run on. Both are replaced by the zeros a compiled file's run starts from, and each substitution is rendered above the trace as a note — a counterexample at one heap is not a counterexample at every heap.
