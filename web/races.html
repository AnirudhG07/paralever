Finding races

When the check refuses, the question changes from "is it safe?" to "show me". Two phases: a scan that is exactly the proof obligation, and a search aimed by what the scan found. The schedule it returns is replayed against the real semantics before it is believed.

Two phases, and what joins them

Phase 1's output is not a yes or no. It names the cells, and phase 2 aims at them. That is the difference between a linear walk and an exponential one.

Phase 1: an empty site list is the proof

The scan walks the term along its reference run. At every fork it collects each pair of children whose footprints conflict, with the offending cells. The result is a list, not a verdict, and its emptiness is equivalent to well-formedness. That is proved in both directions.

That equivalence is what makes this more than a linter. A linter says “no races found” and you believe it or you do not. Here a clean scan is a proof of well-formedness, which is exactly the hypothesis the main theorem wants. Zero false negatives is a theorem, not a tuning result.

The scan is complete because the machine checks for a conflict before letting anyone move. Detection is instantaneous, not retrospective. Note the absence of a read/read clause.

the conflict test 
conflict(a, b)  =  loc(a) == loc(b)  &&  (isWrite(a) || isWrite(b))

nextAccs(pure _)      = []                 # the actions a thread could do NEXT
nextAccs(read l _)    = [read l]
nextAccs(write l _ _) = [write l]
nextAccs(par cs _)    = concat(nextAccs(c) for c in cs)   # through nested forks

step(par cs k, σ) =
    groups = [ nextAccs(c) for c in cs ]                  # one group per child
    if any two distinct groups contain a conflicting pair:  [wrong]
    else …

Phase 2: left-to-right is the worst possible order

A race needs two threads poised at conflicting accesses at the same instant. The one move that destroys that position is letting a thread execute its conflicting access and run on. That is exactly what a naive depth-first search does first. It drives the first child through, finds nothing, then backs up one step at a time until the two sides happen to line up.

Phase 1 already says which locations conflict, so the fix is to try those moves last:

findWrongGuided 
targetsOf(sites) = dedup(concat(s.conflicts for s in sites))   # what phase 1 flagged

consumesTarget(p, σ, targets, i) =          # does successor i give up the position?
    match attribution(p, σ, i).action:
      some a -> a.loc in targets
      none   -> false                       # a join consumes nothing

findWrongGuided(targets, fuel, c):
    if fuel == 0: return NONE
    succs = stepC(c)
    if some i has succs[i] == wrong: return [i]
    hold = [ i for i in indices(succs) if consumesTarget(..., i) ]
    …try the others first, then `hold`

Each thread now advances freely until its next action is a flagged one, and stops there. Once two threads are stopped, the machine reports the race itself. The aiming is a reordering, not a restriction: every successor is still visited, so nothing becomes unfindable. The build checks that the blind and aimed searches agree on small and random trees, and that every schedule the aimed search returns really reaches wrong.

The case that matters forks three threads, where the middle one is innocent. Blind, that thread multiplies the backtracking: 2.7 seconds at eight writes a side, hopeless at twenty. Aimed, it is 34 milliseconds at sixty. There is no backtracking left to multiply, because the innocent thread's moves are never flagged and the two guilty threads stop at their conflicting writes.

The right-hand table is a clean program. Every path has to fail before “no counterexample” comes back, and guidance cannot help, because there are no conflict locations to aim at. That cost is never paid: the search returns at once on an empty scan, and the completeness theorem justifies doing so. Phase 1's quadratic term is the footprint representation, which is a deliberate trade: every other use of a footprint is a decidable membership check.

Replaying the schedule

A schedule is a list of successor indices: at each configuration, which of the available moves to take. The search produces one, and follow walks it against the real step relation. A successful walk is a derivation, and that is proved.

So the printed interleaving is a proof object. The heuristic that found it could be arbitrarily wrong without endangering anything, because what is believed is the replay.

What it prints

race.prl is two threads that each log their arrival and then both write x[0].

race.prl 
buf x[1]
buf log[2]

parallel {
  log[0] := 1
  x[0] := 7
} | {
  log[1] := 1
  x[0] := 9
}
paralever race Examples/Language/race.prl 
step:thread  action              state
0:T0         write [log[0]] ← 1  log[0]↦1, x[0]↦0, log[1]↦0
1:T1         write [log[1]] ← 1  log[0]↦1, x[0]↦0, log[1]↦1
2:T1         write [x[0]] ← 9    pending
2:T0         write [x[0]] ← 7    pending
Parallel aborts at Step 2. Reason: T0, T1 write to: {x[0]}.
Parallel: x[0]↦7
Sequential: x[0]↦9

Both actions at step 2 are marked pending. Neither ran, because the fork aborted when it saw them. A pending step carries the heap as it stands at that instant, with no cell marked as changed.

Why the report shows an abort and no heap diff.

wrong is absorbing, so the parallel program has no final heap at all. The sequential one leaves x[0] ↦ 9. Racy programs are excluded rather than given a behaviour. The sequential heap is printed beside the abort to show what was lost, and the two are not comparable.

A clean program has nothing to show, and says so:

output 
counterexample: none
Sequential: 0↦0, 1↦1, 2↦2

A thousand-step trace is a thousand rows, and the information is at the end. The report keeps the first five steps and the last fourteen, and collapses the middle into a count. The model behind the text is structured: a step knows its thread, its action and its cells. So the same report renders as terminal text and as an editor widget.

In tactic position

Two tactics, for a goal you are writing by hand rather than a file you are checking. paralever_race leaves the goal alone. paralever_check is the one a proof uses: it tries to prove the goal first, one route at a time. It runs the search only when no route discharges the obligation, and then fails with the interleaving attached.

RouteWhat it is
refine par_seq_eq ?_ _ _ <;> grindthe one-liner, with grind on the obligation
the same <;> simp +decide…evaluating it
the same <;> decide…evaluating it in the kernel
parSeqEq_of_runSeq_eq from two wellFormedB_iffsthe per-heap route, for a computed address
par_seq_eq _ _ _ ((wellFormedB_iff _ _).1 ?_)the same for a ParM written by hand

The first route cannot discharge this obligation, and is kept first anyway. The obligation is a closed Boolean computation, so grind treats it as an atom with nothing to rewrite. The routes after it evaluate the term instead. The order is deliberate: a future lemma set, for symbolic programs with nothing to evaluate, belongs before the evaluating routes that could not touch them.

A goal that quantifies over its heap has no values for the search to run on. It is replaced by the zeros a compiled file starts from, and the substitution is noted above the trace. A counterexample at one heap is not a counterexample at every heap.
