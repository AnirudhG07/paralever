paralever

The language

A small imperative language with one unusual property. A statement's footprint is computable from its syntax, so “may these two run together?” is a Bool. It is written either as a .prl file or as Lean notation.

A file, read while Lean elaborates

There is no second compiler. prl_file "sum.prl" parses and compiles the file while Lean elaborates the module that mentions it. The declaration then holds the program as a literal, so by decide sees a program and never the reader.

A program is first-order, so it can also be printed back out. A program can leave the repository as text and come back as the same program. That round trip is a gate in the build, and it runs on every example.

Full detail: docs/prl.md.

The grammar

grammar 
file    ::= stmt* | "paralever" "{" stmt* "}"
stmt    ::= "buf" name ( "[" exp ("," exp)* "]" )? ("at" exp)? ("=" init)?
          | "const" name "=" exp
          | "reg" name ("," name)* ("=" number)?    -- optional: pins an index
          | "free" name
          | "%" reg ":=" addr                       -- load
          | addr ":=" exp                           -- store
          | "%" reg ":=" exp                        -- register assignment
          | "parallel" thread ("|" thread)* label?
          | "parfor" name "in" exp thread label?
          | "for" name "in" exp thread
          | "if" exp thread ("else" (thread | ifstmt))?
          | "while" exp "in" exp thread
          | "def" name "(" param ("," param)* ")" thread
          | name "(" arg ("," arg)* ")"             -- a call, written out where it stands
          | "assert" call "==" call ("on" name ("," name)*)?  -- the file's claim
init    ::= "zeros" | "ones" | "eye" | "arange" | "full" exp
          | ("[")? exp ("," exp)* ("]")?
thread  ::= "{" stmt* "}"
ifstmt  ::= "if" exp thread ("else" (thread | ifstmt))?
param   ::= name | "%" reg
arg     ::= "%" reg | exp
call    ::= name "(" arg ("," arg)* ")"
label   ::= "::" string
addr    ::= "[" exp "]" | name ( "[" exp ("," exp)* "]" )?
exp     ::= exp ("+"|"-"|"*"|"/"|"%") exp | "-"? number | name | "%" reg
          | "min" "(" exp "," exp ")" | "max" "(" exp "," exp ")" | "(" exp ")"
reg     ::= number | name

Comments run from -- to end of line. A line break or a ; separates statements. The optional paralever { … } wrapper means a program pasted out of a Lean file is already a valid .prl file.

Declarations are statements, because free is one: a buffer has a lifetime in the program text. They are allowed only at the top level. A declaration inside one thread of a fork would be visible to that thread alone, so it is rejected.

Memory is declared, not allocated

Memory is total. Every cell exists and holds 0 until written, so a program cannot create or destroy one. A file declares ranges and ends their lifetimes. That is all a layout is.

prl 
buf A[6] = 1, 2, 3, 4, 5, 6   -- the allocator places it
buf C[2, 3] = ones
buf S[4] at 100               -- placed by hand
let g = 0                     -- a variable: a scalar, addressed as `g`
let msg = "hello"             -- one cell per UTF-8 byte, so msg[5]
slice half = C[0..2]          -- a name for two of C's cells; no memory is placed
const n = #half               -- 2, folded while the file compiles
copy half from msg[0..2]      -- cell by cell, in index order
free C                        -- C's lifetime ends here

let is buf with the shape read off the initializer. A variable is a cell of memory, because there is no second kind of state for one to live in. A buffer with no at begins where the previous one ended, so no two live buffers can overlap. One placed by hand is checked against every live buffer, and both are named on failure.

A slice is a view, not a copy. It compiles to a base and a length, so half[i] is C[i]. That is what makes it more than shorthand. A computed subscript is bounded by the range it is written against, so four threads naming four disjoint quarters get four disjoint footprints. The same program written against the whole buffer is refused. A slice is also the one declaration a thread may make, because it places no cells.

free A ends that buffer's lifetime. Two things follow, and nothing else does.

  • ▸

    The name is gone, so any later mention of it is a compile error. That is the useful half: it is how a file says that nothing below this line may touch that memory.

  • ▸

    The space comes back when it was the most recent buffer placed. Declarations are a stack, so the next one lands on those cells. Freeing out of order ends the name and leaves the hole.

Nothing is zeroed and no cell goes away. A buffer declared on a freed range begins holding whatever the last occupant left. The model is an arena, not a heap.

There is deliberately no run-time alloc.

It would cost the main theorem twice. An allocator has to choose an address, and two schedules would choose differently, so the final heaps would differ for reasons that have nothing to do with races. A run-time free is worse: Bernstein's conditions are about reads and writes, so two threads freeing one block is a race the three clauses cannot see. The free above happens at compile time and leaves no trace in the program.

Both buf and free are erased. Neither emits a node, so the compiled program of

prl 
buf A[2]
A[0] := 1
free A

is [0] := 1 on the nose, and the build pins that equality. So no theorem can depend on a declaration. What a declaration decides is which addresses the program names and what the initial heap holds. The theorems are parametric in the heap, so a different layout changes numbers in a #guard, never a proof obligation.

Full detail: docs/layout.md.

Registers are thread-private

A register needs no declaration. Every %name in the file is collected first and given the lowest free index, in order of first appearance. So %acc is one register wherever it occurs, and %0 is register 0 as always.

A fork hands every thread the register file as it stood before the fork, and discards what the threads leave. Two threads using %acc therefore do not interfere, which is why independence is about memory alone. It also means a register written on one side of a fork and read on the other reads a stale value. That is not a race, so the check cannot see it. The parallelizing pass puts its boundaries where no register is live across them.

Addresses, values, and the two readings of %

An address is a compile-time number. Literals, constants, loop variables and arithmetic are all folded. A subscript is range-checked while the file compiles, so A[9] on a six-cell buffer is a compile error rather than a stray write.

A value is arithmetic over registers and folded constants. It has no modulo. So % reads two ways, decided by position: before a name it is a register, between two values it is modulo.

A subscript holding a register cannot be folded. It compiles to a form confined to its own buffer, and it indexes that buffer flat. A bare address holding a register, [%0] := 1, is rejected: there is no buffer to confine it to, so its footprint would be the whole heap.

The price of a computed address is precision, not soundness.

The footprint of dst[%i] := 1 is every cell of dst. So scatter.prl is proved at the declared heap only, although its three threads write three distinct cells. The report says exactly that, in those words.

Loops are unrolled; while is bounded

for and parfor take a compile-time bound and are unrolled, so the program a theorem is about has no loop in it. while c in n runs at most n times and compiles to nested conditionals. The bound is not a shortcut: the program type is inductive, so an unbounded loop cannot be written.

control.prl 
buf n[1] = 3
buf acc[1]

%i := n[0]
%a := 0
while %i in 8 {
  %a := %a + %i
  %i := %i - 1
  acc[0] := %a
}

A conditional's footprint is the union of its branches, so the bounded loop reports every cell any iteration could touch. That is never unsound, and it is why a loop whose iterations really are independent can still look dependent.

Full detail: docs/loops.md.

Functions are written out, not called

def names a list of statements, and a call writes them out where it stands. There is no call constructor and no stack, so a def is a named piece of program text. It costs nothing at run time and it cannot recurse. A cycle of calls is refused, with the chain that closes it.

funcs.prl (the first of its two defs) 
const n = 4

def dot(Out, r, Row, V, m) {
  %s := 0
  for j in m {
    %a := Row[j]
    %b := V[j]
    %s := %s + %a * %b
  }
  Out[r] := %s
}

buf M[4, 4] = arange
buf V[4] = ones
buf Y[4] = zeros

parfor i in n {
  slice row = M[i * n .. i * n + n]
  dot(Y, i, row, V, n)
} :: "rows"

A parameter is a name or a register, told apart by its spelling. A name takes a buffer, a slice or a compile-time value, and is substituted wherever the body uses it. That is why for j in m can unroll inside a body. A register parameter is how a result leaves a call without going through memory.

Every register the body names, and did not take as a parameter, is renamed per call site. Two calls never share one, and a call cannot clobber a register the caller is holding. That also decides what can be scheduled: the pass will not split a chain whose statements share a register, so without the rename three calls would be sequential by construction. Everything downstream sees a program with no trace of a def in it.

Full detail: docs/prl.md § Functions.

Two programs, one claim

Everything above is about one program: does running its forks in parallel reach what running them in order reaches? Someone who has written a sequential sort and a parallel one is asking something else. Do these two programs compute the same thing? That is what assert states.

equiv.prl 
const n = 8

def cmpswap(A, i, j) {
  %x := A[i]
  %y := A[j]
  if %x > %y { A[i] := %y
               A[j] := %x } else { A[i] := %x
               A[j] := %y }
}

-- every pass compares every adjacent pair, left to right: no parallel block at all
def bubble(A, m) {
  for i in m {
    for j in m - 1 { cmpswap(A, j, j + 1) }
  }
}

-- phase p compares the pairs starting at p mod 2, all of them at once
def oddeven(A, m) {
  for p in m {
    parfor q in (m - p % 2) / 2 {
      cmpswap(A, 2 * q + p % 2, 2 * q + p % 2 + 1)
    } :: "phase"
    synchronize
  }
}

buf A[8] = 5, 3, 8, 1, 7, 2, 6, 4

assert bubble(A, n) == oddeven(A, n) on A

print A

The file is compiled twice, once per side. Declarations and initializers are shared, so both programs start from one heap. on A names the buffers compared. A parallel version often needs scratch the sequential one does not, and those cells are allowed to differ.

The claim is cheap because it factors into three checks, and only two of them are about parallelism. Each side agrees with its own sequential reading, which is the main theorem applied twice. What is left is whether two programs with no fork in them compute the same thing.

paralever check reports the claim beside the verdict and exits non-zero when it fails. paralever prove writes the conclusion: every outcome either program reaches, under every schedule of either, holds the same values at the named cells. The third check runs both programs on the declared heap, so that is the heap the claim is about.

Full detail: docs/equivalence.md, including what lifting the claim to every heap would take.

A worked file

sum.prl uses everything at once: constants, two buffers with data, an unrolled parfor with a nested for inside each thread, a private accumulator, and a label.

sum.prl 
const len    = 2
const chunks = 3

buf A[6] = 1, 2, 3, 4, 5, 6
buf out[3]

parfor c in chunks {
  %acc := 0
  for k in len {
    %v   := A[c * len + k]
    %acc := %acc + %v
  }
  out[c] := %acc
} :: "chunked sum"
paralever check 
Examples/Language/sum.prl
  memory    A[6] @0, out[3] @6  (9 cells)
  reads     {A[0], A[1], A[2], A[3], A[4], A[5]}
  writes    {out[0], out[1], out[2]}
  threads   3
  rounds    3 parallel, 9 sequential
  verdict   every heap  Proved: Yes — wfB accepts: the threads' footprints are pairwise independent

Each thread reads its own slice of A and writes its own cell of out. The three footprints are pairwise independent, and the fork turns nine sequential memory operations into three parallel rounds.

What is rejected, and why

Each of these is a compile error carrying a line and a column, and each is pinned as a test. The boundary is as much the specification as the grammar is.

The same language, as Lean notation

A paralever { … } block takes Lean terms for its addresses and values, so any Lean expression of the right type works. A .prl file has none of that, because the reader cannot call the elaborator. It gets constants and loop unrolling instead.

Lean 4 · Examples/Language/Writing.lean

All three threads read cell 2 and each writes a cell of its own. The footprint is a fold over the syntax, so it holds by rfl and the check is decide. Neither line mentions a heap.

Memory in the Lean notation is [l] and a register is %n. That is not a style choice. Declaring a syntax keyword reserves that word for the whole project, so nothing anywhere can be named it afterwards. Writing memory as mem l made def mem impossible, and that was the obvious name for a layout. Brackets reserve nothing.

Every constructor has a form on both surfaces, so a file and a block say the same things. Two Lean forms have no .prl spelling. [A, e] names a cell by range and index, because Lean cannot spell it A[e]. { … } :: "name" labels a region that is not a fork.
