paralever

The language

ParProg is a first-order imperative language with one unusual property: a statement's footprint is computable from its syntax, so "may these two run together?" is a Bool. It is written either as Lean notation or as a .prl file.

A file, read while Lean elaborates

There is no second compiler and no separate toolchain. prl_file "sum.prl" parses and compiles the file during elaboration of the Lean module that mentions it, and the declaration it defines holds the resulting program as a literal. So by decide sees a program, never the reader.

The file exists because a ParProg is first-order and can therefore be printed. Prl.print emits .prl text and prl_file reads it back, so a program can leave the repository — into a bug report, a paper appendix, another tool's output — and come back as the same program. Prl.roundTrips src is the gate on the reader, and it runs on every example in the build.

The grammar

grammar 
file    ::= stmt* | "paralever" "{" stmt* "}"
stmt    ::= "buf" name ( "[" exp ("," exp)* "]" )? ("at" exp)? ("=" init)?
          | "const" name "=" exp
          | "reg" name ("," name)* ("=" number)?    -- optional: pins an index
          | "free" name
          | "%" reg ":=" addr                       -- load
          | addr ":=" exp                           -- store
          | "%" reg ":=" exp                        -- register assignment
          | "parallel" thread ("|" thread)* label?
          | "parfor" name "in" exp thread label?
          | "for" name "in" exp thread
          | "if" exp thread ("else" thread)?
          | "while" exp "in" exp thread
init    ::= "zeros" | "ones" | "eye" | "arange" | "full" exp
          | ("[")? exp ("," exp)* ("]")?
thread  ::= "{" stmt* "}"
label   ::= "::" string
addr    ::= "[" exp "]" | name ( "[" exp ("," exp)* "]" )?
exp     ::= exp ("+"|"-"|"*"|"/"|"%") exp | "-"? number | name | "%" reg
          | "min" "(" exp "," exp ")" | "max" "(" exp "," exp ")" | "(" exp ")"
reg     ::= number | name

Comments run from -- to end of line. Statements are separated by a line break, by ;, or by both. The optional paralever { … } wrapper means a program pasted out of a Lean file is already a valid .prl file.

Declarations are statements because free is one: a buffer has a lifetime in the program text. They are allowed only at the top level, where the whole program sees them — a buf or a free inside one thread of a parallel would be visible to that thread alone, and is rejected.

Memory is declared, not allocated

State is Loc → Val and total: every location exists and holds 0 until written. A program cannot create or destroy a location, because there is nothing to create. What a .prl file does is declare ranges and end their lifetimes, which is what a Layout plus a cursor is.

prl 
buf A[6] = 1, 2, 3, 4, 5, 6   -- the allocator places it
buf C[2, 3] = ones
buf S[4] at 100               -- placed by hand
const n = 2
free C                        -- C's lifetime ends here

A buffer with no at begins where the previous one ended, so no two live buffers can overlap. A buffer with an at was placed by the author, so the compiler checks it against every live buffer and names both on failure.

free A ends A's lifetime. Two things follow, and nothing else does.

  • ▸

    The name is gone. Any later mention of A is a compile error — which is the useful half, since it is how a file states that nothing below this line may touch that memory.

  • ▸

    The space comes back when A is the most recent buffer placed, so buf/free is a stack and the next declaration lands on A's cells. Freeing out of order ends the name's scope and leaves the hole, because the cursor only moves back from the top.

Nothing is zeroed and no location goes away: a buffer declared on a freed range begins holding whatever the previous occupant left. This is an arena, not a heap.

There is deliberately no run-time alloc.

Adding one would cost the main theorem twice over. alloc has to choose an address; two schedules choose differently, so the final heaps differ and par_seq_eq — an equality of heaps — becomes false for reasons that have nothing to do with races. A run-time free is worse: Bernstein's conditions are about reads and writes of locations, so two threads freeing one block, or one freeing while another reads, is a race that w₁∩w₂ = w₁∩r₂ = w₂∩r₁ = ∅ cannot see. The free above avoids both because it happens at compile time and leaves no trace in the program.

Both buf and free are erased. Neither emits a node, so the compiled program of

prl 
buf A[2]
A[0] := 1
free A

is [0] := 1 on the nose, and the build pins that equality. Consequently no theorem about a program can depend on either declaration: wfB, footprintOf, par_seq_eq, time_le and runTask_eq are statements about the ParProg, proved exactly as they are for a program written in Lean. What a declaration does decide is which addresses the program names and what the initial heap is. The theorems are parametric in the heap, so a different layout changes the numbers in a #guard, never a proof obligation.

Registers are thread-private

A register needs no declaration. Every %name in the file is collected before anything is compiled and given the lowest index no numbered register uses, in order of first appearance — so %acc is a register wherever it occurs and %0 is register 0 as always. reg acc = 3 pins a name to an index when that matters.

A parallel block hands each thread the pre-fork register file and discards what the threads leave. Two threads using %acc therefore do not interfere, and that is why independence is about memory alone. It also means a register written on one side of a fork boundary and read on the other reads a stale value — not a race, so wfB cannot see it, which is why the autoparallelizer places its boundaries where no register is live across them.

Addresses, values, and the two readings of %

An address is a compile-time number. The lowering folds it: literals, consts, enclosing loop variables, and + - * / %. A buffer subscript A[i, j] becomes Layout.at "A" [i, j], and the subscript is range-checked then and there — A[9] on buf A[6] is a compile error, not a stray write.

A value is an arithmetic expression over registers and folded constants. It has no modulo, so % in a value position is rejected rather than approximated. % therefore reads two ways, decided by position: in operand position %0 and %acc are registers, and in operator position n % 4 is modulo.

A subscript that mentions a register cannot be folded and compiles to the data-dependent form, which is confined to its array by construction. It must be the only subscript, and it indexes the buffer flat, wrapping on its size. A bare address that mentions a register ([%0] := 1) is rejected: there is no array to confine it to, so its footprint would be the whole heap.

The price of a computed address is precision, not soundness.

The footprint of dst[%i] := 1 is every cell of dst, so scatter.prl is this heap only although its three threads write three distinct cells. The reports say so in those words, because the exact per-heap check finds nothing.

Loops are unrolled; while is bounded

for and parfor take a compile-time bound and are unrolled, so the program a theorem is about has no loop in it. while c in n runs at most n iterations and compiles to nested conditionals. The bound is not a limitation of the implementation: ParM is inductive and Lean 4 has no native coinductive types, so an unbounded loop is unrepresentable.

control.prl 
buf n[1] = 3
buf acc[1]

%i := n[0]
%a := 0
while %i in 8 {
  %a := %a + %i
  %i := %i - 1
  acc[0] := %a
}

A conditional's footprint is the union of its branches, so whileAtMost reports every cell any iteration could touch. Conservative, never unsound — and it is the reason a loop whose iterations are in fact independent can still look dependent to the scheduler.

A worked file

sum.prl uses everything at once: constants, two buffers with initial data, an unrolled parfor over chunks with a nested for inside each thread, a private accumulator, and a label.

sum.prl 
const len    = 2
const chunks = 3

buf A[6] = 1, 2, 3, 4, 5, 6
buf out[3]

parfor c in chunks {
  %acc := 0
  for k in len {
    %v   := A[c * len + k]
    %acc := %acc + %v
  }
  out[c] := %acc
} :: "chunked sum"
paralever check 
Examples/Language/sum.prl
  memory    A[6] @0, out[3] @6  (9 cells)
  reads     {A[0], A[1], A[2], A[3], A[4], A[5]}
  writes    {out[0], out[1], out[2]}
  threads   3
  rounds    3 parallel, 9 sequential
  verdict   independent — par = seq under every schedule (wfB = true)

Each thread reads its own slice of A and writes its own cell of out, so the three footprints are pairwise independent and the parfor collapses nine sequential memory operations into three parallel rounds.

What is rejected, and why

Each of these is a compile error with a line:column, and each is pinned as a test. The boundary is as much the specification as the grammar is.

RejectedBecause
[%0] := 1a register in a bare address: no array to confine it to, so the footprint would be the whole heap
buf A[4] then A[9] := 1a subscript outside its buffer
buf A[4] then A[1, 2] := 1two subscripts on a one-dimensional buffer
buf A[2,2] then A[1, %i] := 1a computed subscript beside a static one
buf B[4] at 2 over buf A[4]at placing one buffer on top of a live one
A[0] := 1 with no buf Aan undeclared buffer
free A then A[0] := 1a buffer used after its lifetime ended
free A twice, or free of a non-buffernothing live by that name
parallel { free A } | { … }a declaration inside a thread, where only part of the program would see it
buf A[4] twicea name declared twice
%i := 7 % 2% as a value operator: the expression language has no modulo
%x := A[0] + 1a load inside an expression; a load is its own statement
buf A[2] = 1, 2, 3more initial values than cells

And the accepted forms those rejections are the boundary of:

prl 
[0] := %acc                     -- a register needs no declaration
buf A[4]
%i := 0
A[%i] := 1                      -- a computed subscript, alone, into one buffer
const n = 2
buf M[n, n]
M[1, 1] := 1                    -- const-folded, range-checked
buf S[4] at 100                 -- hand placement, clear of everything live
[0] := 3; [1] := 4              -- `;` or a line break, either way

The same language, as Lean notation

A paralever { … } block takes Lean terms for its addresses and values, so any Lean expression of the right type works: [n * 2 + 1], an address computed by a Lean function, or a combinator spliced in. A .prl file has none of that, because the reader cannot call the elaborator. The closed expression language, const, and for/parfor unrolling are what it has instead.

All three threads read [2] and each writes a cell of its own — the shared-read case. footprintOf is a fold over the syntax, so the footprint is rfl and the Bernstein check is decide; nothing in those two lines mentions a heap.

Memory in the Lean notation is written [l] and a register %n. That is not a style choice: a syntax "foo" declaration reserves foo as a token for the whole project, so no declaration anywhere could then be named foo. Writing memory as mem l made def mem impossible — the obvious name for a Layout — so the notation uses brackets, which reserve nothing.
