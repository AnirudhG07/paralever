paralever

A parallel program and its sequential counterpart leave the same heap — under every schedule — whenever the forked branches are independent. Proved once in Lean 4; after that, each program owes a single decidable check.

The theorem is about a semantics, not about Lean's runtime. par is a constructor of the program type and its meaning is fixed by an interleaving machine, so there is something to prove. A program that races does not quietly get the equality: it reaches an absorbing wrong, and the tool prints the interleaving that puts it there.

One theorem, then a check

ParSeqEq p q σ says the two programs reach exactly the same terminal configurations from the heap σ: not that one refines the other, not that both satisfy a specification, but that the sets of reachable results coincide. On the surface language, the hypothesis is a Bool.

Lean 4 · Lang/Core/Prog.lean

Everything a user writes per program is h, and h is discharged by by decide. The surface language computes a footprint from the syntax, so wfB tests Bernstein's three conditions at every parallel node without ever running the program.

Shared reads are allowed

Independence is Bernstein's condition — w₁∩w₂ = w₁∩r₂ = w₂∩r₁ = ∅ — and not separation logic's ∗. The difference is the whole reason the method covers real kernels: a matrix multiply writes disjoint cells of C while reading overlapping rows of A and columns of B, which ∗-disjointness refuses and Bernstein admits.

wfB = true
stencil.prl 
const n = 4

buf inp[5] = 1, 2, 3, 4, 5
buf out[4]

parfor i in n {
  %a := inp[i]
  %b := inp[i + 1]
  out[i] := %a + %b
} :: "stencil"

Neighbouring threads read inp[i+1] in common and no cell is written twice. Independent, so par_seq_eq applies at every heap.

race
race.prl 
buf x[1]
buf log[2]

parallel {
  log[0] := 1
  x[0] := 7
} | {
  log[1] := 1
  x[0] := 9
}

Both threads write x[0]. The parallel reading reaches wrong, the sequential reading terminates, and the equality is false — refuted in Lean, not merely unproved.

Three verdicts, no fourth

A program lands in exactly one of three places, and which one is decided by the checks rather than chosen. paralever prove FILE writes the Lean module that carries whichever theorem the verdict licenses.

The same four reports are available as #evals inside Lean, over a program read at elaboration time, so a .prl file can be the subject of a theorem without a build step in between. See the command line.

Why the theorem is not empty

The standing risk in a development like this is proving something true and vacuous. Four facts keep it honest, and each is enforced by the build.

1

Lean's Task cannot host the theorem. Task is a one-field structure with a real body, so (Task.spawn f).get = f () holds by rfl — parallel and sequential would be the same term. Task is a compilation target only; nothing is ever proved about parallelism there.

2

A racy program is exhibited, in Lean, where the conclusion fails. If the hypothesis were decoration, the theorem would hold without it. Examples/Races/Caught.lean is the witness that it does not.

3

A race is an absorbing wrong, not an assumption. Following Reynolds' grainless semantics, a conflicting fork steps to a configuration with no successors. That is what makes the atomic grain irrelevant and keeps racy programs excluded rather than silently assumed away.

4

No sorry, and no native_decide. grep -rn "sorry" Paralever/ is a gate in the build, and every per-program obligation is discharged by the kernel.
