paralever

Paralever is a small language that exists to prove one thing: running a program's threads in parallel leaves exactly what running them in order leaves, and Lean 4 checks it.

Consider two jobs, P1 and P2, sharing one variable x:

Running them in parallel can leave an outcome the sequential run never produces. So for this program you cannot say parallel = sequential.

So the question is: for a given program, is parallel equal to sequential, under every schedule rather than just the one that ran?

par p  ≡  seq p
ParSeqEq: from the same starting heap, the parallel and the sequential program reach exactly the same (result, final heap) pairs. Every schedule, not one of them.

Matrix multiply is ParSeqEq, proved

Examples/Language/matmul.prl (without its header comment) 
const n = 2

buf A[2, 2] = 1, 2, 3, 4
buf B[2, 2] = 5, 6, 7, 8
buf C[2, 2]

parfor i in n {
  for j in n {
    %acc := 0
    for k in n {
      %x := A[i, k]
      %y := B[k, j]
      %acc := %acc + %x * %y
    }
    C[i, j] := %acc
  }
} :: "matmul 2x2"

One thread per row. Each thread writes its own row of C, and every thread reads all of B. That is not a race, and three steps show why: measure what each thread touches, check the three conditions, then state the theorem.

3 · The theorem

Lean 4 · Examples/Language/Files.lean

by decide checks the three conditions on this program. par_seq_eq turns that Boolean into equality of outcomes under every schedule. The proof is one line because the hard theorem was proved once, for all programs.

Shared reads are allowed

Separation logic's ∗ splits memory into disjoint pieces, so two threads may not hold the same cell. Matrix multiply fails that test. Bernstein's condition has no clause on reads, so it admits the program. That one difference is what lets the method reach real kernels.

accepted
stencil.prl 
const n = 4

buf inp[5] = 1, 2, 3, 4, 5
buf out[4]

parfor i in n {
  %a := inp[i]
  %b := inp[i + 1]
  out[i] := %a + %b
} :: "stencil"

Neighbours share the read of inp[i+1]. No cell is written twice. The threads are independent, so the theorem applies at every heap.

refused
race.prl 
buf x[1]
buf log[2]

parallel {
  log[0] := 1
  x[0] := 7
} | {
  log[1] := 1
  x[0] := 9
}

Both threads write x[0]. The parallel reading aborts where the sequential reading finishes, so the equality is false. Lean refutes it rather than leaving it open.

The given heap, and every heap

Every report answers the question twice. At the heap the file declares, an exact search settles it. At every heap, the syntactic check settles it when the footprints are precise enough. A computed address or a branch widens them, and then the general answer is the weaker of the two.

QuestionWhat is provedHow
At the given heap ParSeqEq at the heap the file declares the exact per-heap search, then parSeqEq_of_runSeq_eq
At every heap ParSeqEq at every heap and register file ParProg.par_seq_eq (by decide) ρ σ

If two threads touch one cell and at least one writes, both answers are no. Each refusal is itself proved. The tool then prints the interleaving that reaches wrong, and paralever prove FILE writes the Lean module carrying whichever theorem the two answers license.

Running it yourself

console 
git clone https://github.com/AnirudhG07/paralever && cd paralever
lake exe cache get          # Mathlib oleans, before a first build
lake build paralever        # ./.lake/build/bin/paralever

paralever check Examples/Language/matmul.prl

No solver is needed and nothing is downloaded at run time. The same reports are available as #evals inside Lean, over a file read while Lean elaborates, so a .prl file can be the subject of a theorem with no build step in between. See the command line.

Guarding against vacuity

The standing risk in work like this is proving something true and empty. Four facts rule that out, and the build enforces each one.

1

Lean's Task cannot host the theorem. It is a one-field structure with a real body, so (Task.spawn f).get = f () holds by rfl. That makes the parallel and the sequential program the same term. Task is a compilation target here, and nothing is proved about parallelism on it.

2

A racy program is exhibited in Lean where the conclusion fails. Examples/Races/Caught.lean refutes ParSeqEq for two threads writing one cell. That is what shows the hypothesis to be load-bearing.

3

A race reaches an absorbing wrong, following Reynolds' grainless semantics. A conflicting fork steps to a configuration with no successors. The atomic grain is therefore irrelevant, and racy programs are excluded rather than assumed away.

4

There is no sorry and no native_decide. grep -rn "sorry" Paralever/ is a gate in the build, and the kernel discharges every per-program obligation.
